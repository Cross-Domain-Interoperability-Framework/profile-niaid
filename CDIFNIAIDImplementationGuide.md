# CDIF NIAID Profile — Implementation Guide

# Purpose and scope

The **CDIF NIAID profile** (`cdifNIAID`) is a document-level CDIF profile for dataset records from the [NIAID Data Discovery Portal](https://data.niaid.nih.gov/). It composes cdifCore with niaidDataset, which constrains the NIAID (`nde:`), Bioschemas (`bios:`) and `cdifniaid:` properties those records carry.

cdifDiscovery is not composed, because about one portal record in six has no discovery content. A record that has it also claims `https://w3id.org/cdif/discovery/1.1` as its own `conformsTo` entry, and is validated against that profile separately.

Records in this profile are made from the portal's API by the table-driven converter in [converters/NIAID](https://github.com/Cross-Domain-Interoperability-Framework/converters/tree/main/NIAID). Its [`cdifJSON-LD/`](https://github.com/Cross-Domain-Interoperability-Framework/converters/tree/main/NIAID/cdifJSON-LD) directory holds 140 converted portal records that validate against this profile.

# Conformance

A resource conforms to the CDIF NIAID profile when its catalog record declares conformance to the profile identifier. The catalog record is carried on `schema:subjectOf` as a `dcat:CatalogRecord`:

```json
"schema:subjectOf": {
  "@type": ["schema:CreativeWork", "dcat:CatalogRecord"],
  "dcterms:conformsTo": [
    "https://w3id.org/cdif/niaid/1.0"
  ]
}
```

Other properties added in this profile are optional; conformance requires only that the constraints in the JSON Schema and SHACL rules are satisfied.

## Validation

Two validators ship with this repository:
- **JSON Schema** — `cdifNIAIDStructuredSchema.json` (Draft 2020-12), generated from the source register.
- **SHACL** — `niaidRules.shacl`, a self-contained shapes graph merged from every composing building block plus the profile-level shapes.

The JSON Schema applies to a record **after framing**: the CDIF frame selects the dataset node and wraps multi-valued properties as arrays. `ConformanceValidate.py`, in the [validation](https://github.com/Cross-Domain-Interoperability-Framework/validation) repository, frames the record. It then validates it against the schema and SHACL of every conformance URI the record's catalog record declares, fetched through w3id:

```bash
python ConformanceValidate.py examples/exampleCDIFniaid.json -v
```

The SHACL rules apply to the RDF graph directly, with no framing:

```bash
pyshacl -s niaidRules.shacl -i rdfs -w -df json-ld examples/exampleCDIFniaid.json
```

`-w` lets warnings pass; only `sh:Violation` results fail a record.

Validation is **open-world**: properties not described by the profile are allowed.

# Provenance of the artifacts

The schema and SHACL files are generated from the canonical source register, [metadataBuildingBlocks](https://github.com/Cross-Domain-Interoperability-Framework/metadataBuildingBlocks):

- `cdifNIAIDStructuredSchema.json` ← `tools/resolve_schema.py cdifNIAID`
- `niaidRules.shacl` ← `tools/validate_shacl.py cdifNIAID --emit-shapes`

Source profile directory: `_sources/profiles/cdifCompositeProfile/cdifNIAID/`.

This guide is written by hand, from the descriptions of the NIAID building blocks in
`_sources/niaidProperties/`. It is not regenerated by the sync.

# Namespaces

A cdifNIAID record uses the namespaces cdifCore uses (`schema:`, `dcterms:`, `dcat:`,
`prov:`, `cdif:` and others, explained in the
[cdifCore implementation guide](https://w3id.org/cdif/core/1.1/guide)). It adds three
more for NIAID's own terms. The profile's JSON-LD context binds them, and the JSON
Schema requires these exact IRIs when a record's `@context` declares the prefixes:

| Prefix | IRI | Defined by | Holds |
|---|---|---|---|
| `schema:` | `http://schema.org/` | [schema.org](https://schema.org/) | Most of the record, including NIAID terms that schema.org already has (`schema:infectiousAgent`, `schema:healthCondition`, `schema:archivedAt`) |
| `bios:` | `https://bioschemas.org/` | [Bioschemas](https://bioschemas.org/) | Bioschemas terms whose definition matches NIAID's: the sample properties and `bios:alternateIdentifier` |
| `nde:` | `https://discovery.biothings.io/ns/nde/` | NIAID's [nde-schemas](https://github.com/NIAID-Data-Ecosystem/nde-schemas) | Terms NIAID's schema declares and neither schema.org nor Bioschemas has, such as `nde:species` and `nde:pmid` |
| `cdifniaid:` | `https://w3id.org/cdif/niaid/terms/` | this profile ([below](#the-cdifniaid-namespace)) | Names the portal uses that no published vocabulary declares |

## Choosing the namespace for a NIAID property

The portal's JSON uses bare names (`species`, `pmid`, `projectNumSplit`). Each name is
given exactly one namespace:

1. **`schema:`** when the name is a schema.org term used with its schema.org meaning.
2. **`bios:`** when Bioschemas defines the same term. NIAID's and Bioschemas'
   definitions were compared term by term; a matching Bioschemas term is used even
   where NIAID's schema also declares it.
3. **`nde:`** when NIAID's schema declares the term and neither of the above does.
4. **`cdifniaid:`** when the portal uses the name but no vocabulary declares it.

The [mapping table](https://github.com/Cross-Domain-Interoperability-Framework/converters/blob/main/mappings/niaid-to-cdif.sssom.tsv)
records the choice for every name.

## The cdifniaid namespace

The portal's records carry some names that appear in no vocabulary: neither schema.org,
Bioschemas nor NIAID's published schema declares them. Most are the parts of an NIH
project number, which the portal splits out of a grant identifier. Rather than drop
that content, or put it in a namespace whose owner never defined it, CDIF gives these
names its own namespace, `cdifniaid:`, and defines them here.

- **This guide is the definition.** The terms are defined in the cdifNIAID profile's
  building blocks and in the table below, and nowhere else.
- **The IRIs do not resolve yet.** `https://w3id.org/cdif/niaid/terms/commonName` and
  its siblings are names, not yet addresses; treat them as you would any other
  identifier. Like other `cdif:` terms, they are defined by CDIF and nowhere else.
- **They sit under `terms/`** so that the profile URI `https://w3id.org/cdif/niaid/1.0`
  is never compacted to a `cdifniaid:` CURIE by a JSON-LD processor.
- **The list is closed.** The converter keeps a portal name it does not know under
  `cdifniaid:` with a note, so that nothing is lost, but such a term is undefined. The
  converter's check fails if any of its example records contains one. A new name needs
  a namespace and a row in the mapping table.

The cdifniaid terms:

| Term | On | Value | Definition |
|---|---|---|---|
| `cdifniaid:assayformat` | dataset | text | The assay format, as the portal gives it |
| `cdifniaid:publication` | dataset | text, digits | PubMed id of a publication about the dataset |
| `cdifniaid:correctionApproved` | `schema:sourceOrganization` | boolean | A correction to the portal's record of the project has been approved |
| `cdifniaid:commonName` | `schema:DefinedTerm` | text | The common name of a taxon, e.g. Human for Homo sapiens |
| `cdifniaid:projectNumSplit` | `schema:MonetaryGrant` | object | The parts of an NIH project number such as `5R01AI012345-03`, in the seven terms below |
| `cdifniaid:applTypeCode` | project number | text | Application type, e.g. `5` for a non-competing continuation |
| `cdifniaid:activityCode` | project number | text | Activity code, e.g. `R01` |
| `cdifniaid:icCode` | project number | text | The NIH institute or center, e.g. `AI` for NIAID |
| `cdifniaid:serialNum` | project number | text | Serial number of the grant, e.g. `012345` |
| `cdifniaid:supportYear` | project number | text | Year of support, e.g. `03` |
| `cdifniaid:fullSupportYear` | project number | text | Year of support with any suffix |
| `cdifniaid:suffixCode` | project number | text | Suffix, e.g. `S1` for a supplement |

# Properties from cdifCore

cdifNIAID composes cdifCore, so a record must meet every cdifCore requirement: identity,
name, dates, license and access, agents, distributions and the catalog record. Those
properties are not repeated here. See the
**[cdifCore implementation guide](https://w3id.org/cdif/core/1.1/guide)** for them, and
the [cdifDiscovery implementation guide](https://w3id.org/cdif/discovery/1.1/guide) for
the discovery properties (`schema:measurementTechnique`, `schema:variableMeasured`,
spatial and temporal coverage) of a record that also claims discovery.

The sections below cover only what cdifNIAID adds: NIAID's own properties, and the
NIAID detail it allows or requires on some cdifCore and cdifDiscovery properties.
Everything is optional except `schema:includedInDataCatalog` and the conformance
declaration. Every property accepts one value or an array, because framing collapses a
one-element array to its value.

# Dataset properties

## Required

| Property | Value | Meaning |
|---|---|---|
| `schema:includedInDataCatalog` | [NIAID data catalog](#schemadatacatalog) or `@id` reference | The repositories holding the dataset, which the portal aggregates from |
| `schema:subjectOf` / `dcterms:conformsTo` | contains `{"@id": "https://w3id.org/cdif/niaid/1.0"}` | The catalog record declares the profile ([Conformance](#conformance)) |

## NIAID properties

| Property | Value | Meaning |
|---|---|---|
| `nde:date` | date | The portal's summary date for the record |
| `nde:species` | [NIAID defined terms](#schemadefinedterm) | Host organisms associated with the dataset, e.g. Homo sapiens (the NIAID Blueprint's host); the pathogen is in `schema:infectiousAgent` |
| `nde:nctid` | text, `NCT` and eight digits | ClinicalTrials.gov identifier of the study |
| `nde:citedBy` | text or [cited work](#schemacreativework) | Works that cite the dataset |
| `nde:curatedBy` | [curator](#curator) | Who curated the record, and from which version of their catalog |
| `nde:isBasisFor` | [related resource](#related-resource) | Resources based on this dataset |
| `nde:sample` | [sample or sample collection](#samples) | The samples used to generate the dataset, or a collection of them |
| `bios:alternateIdentifier` | text | Identifiers beyond the one `schema:identifier` holds |
| `cdifniaid:assayformat` | text | The assay format, as the portal gives it |
| `cdifniaid:publication` | text, digits | PubMed ids of publications about the dataset |

## NIAID detail on schema.org properties

These are schema.org properties. Where they hold the NIAID detail listed, the value must
have the NIAID form; otherwise cdifCore's or cdifDiscovery's own rules apply.

| Property | NIAID form | Meaning |
|---|---|---|
| `schema:infectiousAgent` | [NIAID defined terms](#schemadefinedterm) | Infectious agents the dataset is about |
| `schema:healthCondition` | [NIAID defined terms](#schemadefinedterm) | Health conditions the dataset is about |
| `schema:keywords` | text or NIAID defined term | Keyword terms, such as the dataset's EDAM topic categories, with NIAID's annotations |
| `schema:measurementTechnique` | text or NIAID defined term | Measurement techniques, with NIAID's annotations |
| `schema:variableMeasured` | text or NIAID defined term | Variables, with NIAID's annotations |
| `schema:citation` | text or [cited work](#schemacreativework) | Citations, with NIAID's PubMed id, DOI and journal names |
| `schema:funding` | [NIAID monetary grant](#schemamonetarygrant) or `@id` reference | Grants, with the parts of an NIH project number |
| `schema:spatialCoverage` | [NIAID place](#schemaplace) or `@id` reference | Places, with NIAID's administrative type |
| `schema:sourceOrganization` | object, with optional `cdifniaid:correctionApproved` | Projects and programs the dataset comes from |

# NIAID properties on other types

NIAID adds properties to five schema.org types. Each set is a building block that
requires the type, so a node carrying one of these properties must declare it; the
converter types the nodes the portal leaves untyped.

## schema:DefinedTerm

Used for `nde:species`, `schema:infectiousAgent` and `schema:healthCondition`, and for
the `schema:keywords`, `schema:measurementTechnique` and `schema:variableMeasured` items
that carry an annotation. The portal annotates every term it attaches to a dataset.

| Property | Value | Meaning |
|---|---|---|
| `nde:isCurated` | boolean | Whether a curator checked the term against its source text |
| `nde:originalName` | text | The text in the source record the term was matched from |
| `nde:curatedBy` | [curator](#curator) | Who or what produced or checked the annotation, often software (PubTator, GPT-4o-mini, the Biothings API) |
| `cdifniaid:commonName` | text | The common name of a taxon, e.g. Human |

These annotations describe one record's use of the term (what text it was matched from,
who checked it), so a term is a node of its own record, not the ontology term itself.
It links to the ontology term with `schema:sameAs` `{"@id": ...}`, its IRI (for example
`http://purl.obolibrary.org/obo/NCBITaxon_9606`). Giving the node the IRI as its `@id`
would merge every record's annotations onto the one shared term. An NCIT term links to
both of NCIT's IRIs, OBO's (`http://purl.obolibrary.org/obo/NCIT_C16585`) and NCI's own
(`http://ncicb.nci.nih.gov/xml/owl/EVS/Thesaurus.owl#C16585`).

## schema:MonetaryGrant

Used for `schema:funding`. CDIF's own grant properties apply.

| Property | Value | Meaning |
|---|---|---|
| `cdifniaid:projectNumSplit` | object | The parts of an NIH project number, in the terms listed under [the cdifniaid namespace](#the-cdifniaid-namespace) |

## schema:CreativeWork

A `schema:CreativeWork` or `schema:ScholarlyArticle`, used for the `schema:citation` and
`nde:citedBy` items that carry one of these properties.

| Property | Value | Meaning |
|---|---|---|
| `nde:pmid` | text, digits | The PubMed id |
| `nde:doi` | text | The DOI, as the portal gives it |
| `nde:journalName` | text | The journal's name |
| `nde:journalNameAbbrev` | text | The journal's abbreviated name |

## schema:Place

Used for `schema:spatialCoverage`.

| Property | Value | Meaning |
|---|---|---|
| `nde:administrativeType` | text | The kind of administrative area, e.g. `country` |

## schema:DataCatalog

Used for `schema:includedInDataCatalog`.

| Property | Value | Meaning |
|---|---|---|
| `schema:archivedAt` | URL | The dataset's page in this catalog |
| `nde:versionDate` | date | The date of the version of the catalog the portal harvested |

## Curator

The value of `nde:curatedBy`, on the dataset or on a defined term: an agent, software
application or catalog. The portal types it as `schema:SoftwareApplication`,
`schema:Organization` or `schema:DataCatalog`, so the type is not constrained. It has
`schema:name`, `schema:url`, `schema:dateModified` and, for a catalog, `nde:versionDate`.

## Related resource

The value of `nde:isBasisFor`: an object with `schema:name`, `nde:doi`, and
`nde:relationship`, how the resource is related (e.g. "has part" or "is part of").

## Samples

The value of `nde:sample` is a sample or a sample collection.

- **A sample** is a Bioschemas sample (`nde:Sample` is NIAID's subclass of it). It uses
  the `bios:` sample terms (`bios:sampleType`, `bios:collectionMethod`,
  `bios:dateCollected`, `bios:locationOfOrigin`, `bios:anatomicalStructure`,
  `bios:developmentalStage`, `bios:sex`, `bios:sampleQuantity`, `bios:isControl` and
  others), plus `nde:species`, `nde:cellType`, `nde:associatedGenotype`, and
  `schema:aggregateElement` for a sample within it.
- **A sample collection** must be typed `nde:SampleCollection`, so that it is not taken
  for a sample. It has `schema:numberOfItems` (a `schema:QuantitativeValue`), and its
  samples in `schema:itemListElement` or `schema:aggregateElement`.

# The NIAID Blueprint

NIAID's *[Blueprint for Including Digital Objects in the NIAID Data Ecosystem](https://doi.org/10.5281/zenodo.17161561)*
(v2, 26 September 2025) asks repositories for 17 schema.org-based elements on every dataset,
with default identifiers and vocabularies. Its host is `nde:species` here, and its funder
and grant are `schema:funding`. The profile's SHACL checks a record's root dataset for
each element with an `sh:Warning`: a record learns what it lacks against the Blueprint
without failing cdifNIAID, because CDIF does not require them all.

The converter adds the Blueprint's default identifiers where it can by exact match: an
SPDX identifier for a Creative Commons or SPDX license, a ROR id for a named funder or
organization author, and an ISO 3166 code for a place named as a country. The converter
can also write a record as an instance of GO FAIR US's CEDAR template for the Blueprint
and report how complete it is; see
[converters/NIAID/blueprintCEDAR](https://github.com/Cross-Domain-Interoperability-Framework/converters/tree/main/NIAID/blueprintCEDAR).

# Portal names that are not properties

Some names in the portal's JSON have no property in this profile. The converter turns
them into CDIF constructs instead:

- The `fromGPT`, `fromPMID`, `fromEXTRACT` and `fromNCT` flags become one sentence each
  ("Metadata source from GPT.") on the catalog record's description.
- A term's `classification` becomes a keyword, and its `displayName` its
  `schema:alternateName`.
- A person's `role` becomes a `schema:contributor` that is a `schema:Role` holding the
  person, CDIF's pattern for roles.
- `isRelatedTo` becomes a `schema:relatedLink` LinkRole, with `schema:linkRelationship`
  "related to" and the portal's relationship in its description.
- A temporal interval with more than dates becomes a `schema:temporalCoverage` interval
  whose description gives the rest (`nde:name: ...; nde:temporalType: ...`).
- A place's `country` becomes its name, and its `locationType` the name term's
  `schema:about`.
- The access levels Open, Restricted and Closed in `conditionsOfAccess` become
  `schema:CreativeWork` links to the COAR access rights open access, restricted access
  and metadata only access, named with the portal's word.

The converter's [README](https://github.com/Cross-Domain-Interoperability-Framework/converters/blob/main/NIAID/README.md)
covers these, and the sentinel values it writes where a record lacks something cdifCore
requires.
